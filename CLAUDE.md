# synth

Azure OpenAI resource, credentials in `conf` (gitignored — treat as a secret).

## Files

- `conf` — env-style config: `AZURE_API_KEY`, `AZURE_API_BASE`, `AZURE_API_VERSION`. Comment notes the only working deployment.
- `azure_llm.py` — small client library with three functions:
  - `chat(prompt)` — plain completion via the Chat Completions API.
  - `chat_thinking(prompt, effort="high")` — reasoning-mode completion via the Responses API (`reasoning.effort`).
  - `chat_search(prompt)` — web-search-grounded completion via the Responses API (`tools=[{"type": "web_search"}]`), returns `(text, citations)`.
- `synth` — the source methodology document: strategy for building synthetic RAG eval sets (question taxonomy, noise transformation layers, binary-decomposition scoring, sizing rules). `litmus` is the implementation of this spec.
- `litmus` — the spec file for the `litmus` Python package (data models, tier configs, module architecture, build order). Not to be confused with the `src/litmus/` package below, which implements it.
- `sample1/` — 13 real FDA drug label PDFs (Ozempic, Mounjaro, etc), used as a realistic corpus for live tests and manual trials.
- `src/litmus/` — the `litmus` pip package implementing the spec. See below.

## Notes

- Only the `gpt-5.4` deployment is live on this resource; other model IDs in the catalog (`/openai/models`) are listed but not deployed — don't assume they work without testing. Confirmed via a direct `/embeddings` call: `text-embedding-3-small` and `text-embedding-ada-002` both 404 (`DeploymentNotFound`) despite appearing in the catalog. This is why `litmus` uses local `sentence-transformers` embeddings instead of Azure.
- Chat Completions API rejects the `web_search` tool type (`function`/`custom` only). Web search and reasoning-effort both require the Responses API (`/openai/responses`), not `/chat/completions`.
- `gpt-5.4` uses `max_completion_tokens`, not `max_tokens`, when called directly via `azure_llm.py`. `litmus` calls the model through `litellm.completion(model="azure/gpt-5.4", ...)` instead, which uses `max_tokens` in its own interface and translates internally — both `max_tokens` and `reasoning_effort` were confirmed to work through litellm against this deployment.

# litmus (the package, `src/litmus/`)

Synthetic eval-set generation and binary-decomposition scoring for RAG systems, implementing the spec in the repo-root `litmus` file. Two-call public API: `litmus.generate(docs_dir, tier=...)` → `EvalSet`, then `litmus.evaluate(eval_set, rag=my_rag)` → `EvalResults`. See `README.md` for the developer-facing guide.

## Package layout

```
src/litmus/
├── __init__.py, api.py     public API surface
├── models.py               all dataclasses/enums (EvalRecord, EvalSet, RecordResult, EvalResults, ...)
├── config.py                TIER_CONFIG, default weights, diagnostic thresholds, sizing table
├── version.py                semver bump, staleness detection
├── llm/client.py             litellm wrapper: conf-loading, retry, JSON extraction, sync+async
├── llm/cost.py                tiktoken counting, litellm cost-map lookup with fallback
├── cache/manager.py          LLM response cache + generate/evaluate checkpoint/resume
├── ingest/                   loader (txt/md/pdf/docx/html/csv), chunker, local embedder, contradiction_detector
├── generate/                 prompts, bridge-entity detection, 9 question-type generators, 7 noise layers,
│                             leakage filter, corpus-aware sizing, eval-set self-validation, orchestrator
├── evaluate/                 RAG runner, retrieval scorer, binary-decomposition judge, intent scorer,
│                             chunk discovery, judge prompts, diagnostics (yes-rate/phi/health), orchestrator
├── report/                   rich terminal summary, HTML report, pandas export, run comparison, CSV review
└── cli.py                    typer CLI (generate/evaluate/validate/staleness/compare/report/review-*)
```

Why a `src/` layout: the repo root already has a file named `litmus` (the spec doc) — putting the package at `src/litmus/` avoids a same-name collision on disk while keeping the importable package name `litmus`.

## Key design decisions

1. **litellm for all LLM calls**, defaulting to `azure/gpt-5.4` (this repo's confirmed-working deployment, loaded from the repo-root `conf` file automatically). Any litellm model string works if the caller sets that provider's own env vars.
2. **Local embeddings, not Azure.** No embeddings deployment is confirmed live on the configured Azure resource (see top-of-file notes) — `ingest/embedder.py` uses `sentence-transformers` (`all-MiniLM-L6-v2`) entirely locally. Only used for contradiction-candidate pre-filtering, not for the RAG's own retrieval (that's the caller's system under test).
3. **`truststore.inject_into_ssl()` before any Hugging Face network call.** On the dev machine this code was built on, Python's default SSL context fails `CERTIFICATE_VERIFY_FAILED` against `huggingface.co` even though the system trust store (and `curl`) verify it fine — a certifi-bundle-vs-system-store mismatch, not an actual security issue. `truststore` routes verification through the OS trust store instead. Set this up once in `ingest/embedder.py` before importing `sentence_transformers`.
4. **Thread pool concurrency, not asyncio, for `max_workers>1`.** The question-type generators and the binary-decomposition judge are synchronous functions built on `LLMClient.complete_json` (a blocking `litellm.completion` call). Rather than maintaining an async twin of every generator/scorer function, `generate/orchestrator.py` and `evaluate/orchestrator.py` parallelize via `ThreadPoolExecutor` — the blocking HTTP call releases the GIL while waiting on the network, so this gets real concurrency without doubling the codebase. `evaluate/runner.py` (running the *user's* RAG callable) and `llm/client.py`'s `acomplete`/`amap` do have real asyncio paths, since those are the pieces most likely to be called from an already-async context.
5. **Binary decomposition, not holistic scoring**, per the source methodology doc's Section 6.2 (citing Cho et al. 2026 / BINEVAL). Every dimension score traces to specific yes/no verdicts with reasons — `results.records[0].faithfulness.verdicts["F2"].reason` always answers "why did this fail?"
6. **Tier controls everything**, not just question count: question-type mix, noise-layer mix, binary-question count/dimensions, retrieval metrics, and which quality checks run are all keyed off `TIER_CONFIG` in `config.py`. Each tier is a self-contained strategy, matching the spec's explicit instruction that tiers are not subsets of each other.
7. **Scoring is decoupled from generation tier.** `evaluate()`'s `scoring` param accepts `None` (tier default), `"mvp"` (force 9Q/3D), `"full"` (force 24Q/5D), or a fully custom `list[BinaryQuestion]` — independent of what tier generated the eval set.
8. **Set recall over chunk recall** as the headline retrieval metric (`evaluate/retrieval_scorer.py`), because for cross-doc questions chunk-level recall can show 50% on a completely unanswerable case. Retrieved-context-to-gold-chunk matching is done via normalized-substring + Jaccard-token-overlap on free text (the RAG callable returns text, not chunk IDs) — deliberately not embedding-based, so it's fast and deterministic in the evaluation hot loop.
9. **Programmatic typo injection, not LLM-based** (`generate/noise.py`), per the source doc's explicit warning that LLMs over-correct or produce unrealistic typos. Uses a small realistic-error-pattern set (adjacent-key swap, dropped letter, doubled letter, phonetic misspelling) seeded for reproducibility.
10. **Cache + checkpoint by default.** `cache/manager.py` keys LLM responses on `sha256(prompt+model+temperature)`; `generate()`/`evaluate()` checkpoint progress (per question-type batch / per scored record) so an interrupted run resumes rather than re-paying for identical calls.
11. **Stub-RAG detection.** `evaluate/diagnostics.py::detect_stub_rag()` runs automatically at the end of every `evaluate()` call. It flags two signals: placeholder text matching the README quickstart's example stub (`"..."`, `"chunk text 1"`), and a RAG callable that returned byte-identical output for every question (real retrieval varies with the question; a constant response means nothing upstream ran). Warnings are logged during the run, attached to `results.metadata["stub_rag_warnings"]`, and printed in red above the score table in `results.summary()` — so running the quickstart verbatim without wiring up a real RAG produces a loud warning instead of silently-meaningless scores.

## Testing philosophy — no mocking

This project's explicit policy (confirmed with the user, not a default) is: **do not mock the LLM in tests.** If a test exercises LLM-touching code, it makes a real call against the configured `gpt-5.4` deployment and is marked `@pytest.mark.live`; if credentials aren't available it skips (`pytest.skip`), it never falls back to a mocked response. Rationale: a mock that encodes assumptions about what the LLM "should" return is exactly the kind of thing that silently drifts from reality and gives false confidence.

- `tests/test_*.py` (unmarked) — pure-logic unit tests: chunker, sizing formula, retrieval scoring/matching, phi-coefficient math, model (de)serialization, typo injection, cache manager, version bumping, JSON extraction, token counting. No LLM calls, fast, deterministic.
- `tests/test_fuzz.py` — Hypothesis-based property tests over the same pure-logic surface (chunker never crashes/drops content on arbitrary text, typo injection preserves word count, sizing formula stays bounded and monotonic across tiers, phi-coefficient stays in `[-1, 1]` including zero-variance edge cases).
- `tests/test_live_end_to_end.py` (`@pytest.mark.live`) — real calls against `azure/gpt-5.4`: question generation from the real `sample1/` drug-label PDFs, the leakage filter, contradiction detection on the fixture corpus's deliberate PTO-policy conflict, the binary-decomposition judge catching a fabricated number and rewarding a faithful answer, and full `generate()`→`evaluate()` pipeline runs.
- `tests/fixtures/corpus/` — small hand-authored fixture docs (pricing/support/HR-policy/security, Northbeam-branded) used by both fast and live tests. Includes a deliberate contradiction (2023 PTO policy says uncapped carryover; a 2025 amendment caps it at 40 hours) specifically so contradiction-detection has something real to find.

Run `pytest` for the fast suite (CI-safe, no cost); run `pytest -m live` separately when you want to verify against the real model (costs a small amount, takes several minutes for the full file since it generates/evaluates real eval records against the drug-label corpus).

**Where live test output goes.** The three full-pipeline live tests (`test_full_generate_pipeline_minimal_tier`, `test_full_evaluate_pipeline_against_generated_set`, `test_evaluate_with_perfect_rag_scores_high`) write their generated eval sets, evaluation results, and LLM caches to `tests/.live_runs/<timestamp>/<test_name>/` — not pytest's default `tmp_path` (which is auto-deleted/rotated and lives outside the repo under a system temp root). Every live test run gets a fresh timestamped subdirectory, so re-running the suite never overwrites a previous run's artifacts, and the `live_run_dir` fixture (in `tests/conftest.py`) prints the resolved path at the start of each test session. `tests/.live_runs/` is gitignored. The library itself follows the same principle: `generate()`/`evaluate()` always log the resolved absolute path of `save_path` and `cache_dir` (not the possibly-relative path the caller passed), and explicitly log when no `save_path` was given at all, so it's never ambiguous whether — or where — something was written to disk.

## Extending the system

- **New question type:** add a prompt template to `generate/prompts.py`, a generator function to `generate/question_types.py` (returning a dict with `question`/`gold_answer`/`intent_points`/`gold_chunk_ids`/`source_doc_ids`), wire it into `_generate_type_batch` in `generate/orchestrator.py`, and add it to the relevant tier's `question_types` proportions in `config.py`.
- **New noise layer:** add a prompt template to `generate/prompts.py`, an `apply_*` function to `generate/noise.py`, register it in `NOISE_TRANSFORMATION_STRATEGY` in `config.py`, and wire the layer name into `apply_noise_layers`.
- **New binary question / dimension:** binary questions are just `BinaryQuestion(id, dimension, text, weight)` — pass a custom list to `evaluate(..., scoring=[...])` without touching library code at all. To change the *tier defaults*, edit `MVP_QUESTIONS`/`EXHAUSTIVE_QUESTIONS` in `evaluate/answer_scorer.py`.
- **New retrieval metric:** add computation to `evaluate/retrieval_scorer.py`'s `score_retrieval`, add a field to `RetrievalScore`/`RecordResult` in `models.py`, and gate it behind the tier's `retrieval_metrics` list in `config.py`.

## Eval study results (`eval_study/`, see `eval_plan.md`)

A scoped-down run of `eval_plan.md`'s 3-study validation plan. Code lives in `eval_study/`, artifacts in `results/`, final tables in `results/tables/`. Not yet a full-scale run — sizes were deliberately cut for fast iteration (see `eval_study/config.py`'s scoped-size constants); scaling up is a config change, not a rewrite.

**Study 1 — Judge calibration (RAGTruth, Table 1):** 110 stratified QA rows (~29% hallucination rate preserved), F1/F2/F3 only. **Cohen's kappa = 0.48** — moderate agreement, well under the spec's 0.8 working threshold. Judge over-flags: predicted hallucination on 52% of responses vs. 29% ground truth (precision 0.53, recall 0.94) — catches most real hallucinations but with a high false-positive rate. F2 (fabricated-fact check) is the strongest sub-question (κ=0.60); F1 the weakest. **Not yet evidence the judge is reliable enough to be a sole faithfulness gate.**

**Study 2 — litmus vs Ragas (EnterpriseRAG-Bench slice + MuSiQue passages, Tables 2-3):** First pass showed litmus generating **zero** cross_doc questions on both corpora and `scoring_health()` saturating to "broken"/"needs_work". Investigating surfaced **three real bugs**, all fixed and verified (see below), then a fully clean re-run (isolated `cache_dir` per corpus, verified zero record overlap between corpus A and B) produced the current Table 2/3 numbers:
- **Corpus A (EnterpriseRAG-Bench, 50 docs):** litmus generated 38 records (12 single_chunk, **11 cross_doc**, 8 unanswerable, 7 adversarial; 23 bridge-entity candidates found) — `scoring_health()` = **"broken"** (spreads: faithfulness 0.08, correctness 0.13, abstention 0.21). Ragas generated 39 rows, evenly split single/multi-hop-abstract/multi-hop-specific (13 each) — `scoring_health()` = **"needs_work"**, and notably *better* spread than litmus here (faithfulness 0.28, correctness 0.23, abstention 0.18). Ragas wins this comparison on this corpus.
- **Corpus B (MuSiQue passages, 372 chunks):** litmus generated 24 records (5 single_chunk, **2 cross_doc**, 12 unanswerable, 5 adversarial; 101 bridge-entity candidates found — far more than corpus A, consistent with MuSiQue being curated for cross-document entity overlap, but few converted to final cross_doc records due to leakage-filter discards). Ragas generated 18 rows. Both scored **"broken"** with near-zero faithfulness/correctness spread (litmus: 0.04/0.13; ragas: 0.00/0.06) — our `SimpleRAG` test pipeline performed too well on this corpus for either eval set to discriminate on those dimensions.
- Ragas's output included qualitatively degenerate questions on both corpora — keyword-soup non-questions, garbled multi-clause prose (see `results/qualitative_review_corpus_*.md`, captured on the pre-fix litmus sets but Ragas's own output is unaffected by the litmus-side bugs). Litmus's structural edge remains **guaranteed question-type/noise coverage** (unanswerable, adversarial, noise-injected, and now real cross-doc) vs. Ragas's 100% single/multi-hop output with none of those categories — but this run does NOT show litmus's cross-doc questions or overall scoring outperforming Ragas's on the diagnostic itself; corpus A actually favors Ragas on discrimination. Report this honestly rather than spinning it.

**Study 3 — Leakage filter (MuSiQue, Table 4):** 80% discard rate on litmus's own generated questions over MuSiQue passages (30 answerable candidates checked, 24 discarded as parametric-memory-answerable). Clean, strong result — but measures filter sensitivity on litmus's own generation, not a reproduction of SeedRG's leakage rates on MuSiQue's original human-written questions. Predates all three bugs below; unaffected by any of them (single `generate()` call, no cross-corpus checkpoint sharing).

**Ablation — medium tier on `sample1/` FDA labels (Table 5, litmus-only, no Ragas):** Run after Study 2's `scoring_health()` first saturated, to check whether a harder corpus+tier alone fixes it (before the bridge-entity root cause was known). After the bridge-entity + JSON-array fixes: 25 bridge candidates found, 6 real cross_doc questions generated, document coverage 69%→85%, **correctness spread 0.32 and abstention 0.26 (both above the 0.20 healthy threshold)** — the best discrimination result across the whole study. Faithfulness stayed saturated (F1-F3 ~0.87-0.90) because `SimpleRAG` only ever echoes retrieved context and rarely fabricates regardless of question difficulty. Ran as a single isolated `generate()`+`evaluate()` call — unaffected by the checkpoint-collision bug, numbers stand as originally reported.

**Three real bugs found and fixed via this process (not corpus selection issues), all verified against clean re-runs:**

1. **Bridge-entity scan under-sampled large corpora.** `generate/orchestrator.py` called `find_bridge_candidates(chunks, client, max_chunks_to_scan=min(len(chunks), 40))`, which scanned a **prefix** of `chunks.values()`. Since `chunk_documents()` (`ingest/chunker.py`) inserts chunks doc-by-doc, a 40-chunk prefix of a 50-doc corpus covered only ~15 docs. **Fixed:** `generate/bridge.py` now has `_stratified_sample()`, round-robins across documents; `orchestrator.py`'s scan limit scales with document count (`max(40, len(docs) * 3)`). Covered by `tests/test_bridge.py`.
2. **JSON-array prompts silently returned empty results under Azure JSON mode.** Two prompts ask for "a JSON array" (`bridge.py`'s entity extraction, `noise.py`'s `TERM_EXTRACTION_PROMPT`) and call sites checked `isinstance(result, list)`. Azure/OpenAI JSON mode cannot return a bare top-level array — it wraps it under a single key (`{"json": [...]}`, key varies) the code never unwrapped. **Fixed:** `llm/client.py` adds `extract_json_array()` + `LLMClient.complete_json_array()`. Covered by new cases in `tests/test_llm_client.py`.
3. **Checkpoint keys were not scoped per corpus/eval-set — silent cross-contamination when reusing a `cache_dir`.** `generate/orchestrator.py` used a flat `checkpoint_key = f"generate:{type_name}"`, and `evaluate/orchestrator.py` used a flat `"evaluate:results"` — neither identified *which* corpus/eval-set was being processed. Running `generate()`/`evaluate()` on two different corpora sharing a `cache_dir` caused the second call to silently "resume" the first call's cached records. **Confirmed real:** an early re-run of corpus A/B shared 18 identical FDA-drug-label questions despite corpus B being MuSiQue-derived. **Fixed:** `generate/orchestrator.py` adds `_checkpoint_scope(docs_dir, tier)`; `evaluate/orchestrator.py` adds `_checkpoint_key(eval_set, scoring)` — both sha256-based, included in every checkpoint key now. Covered by `tests/test_generate_orchestrator.py` and `tests/test_evaluate_orchestrator.py`. **Verified fixed:** the final clean re-run (separate `cache_dir` per corpus, as an extra safety margin) confirmed zero question overlap between corpus A's and corpus B's results.

All three bugs were masked by broad `except Exception: return []`-style fallbacks or by checkpoint/resume logic that doesn't verify what it's resuming — worth keeping in mind generally: when a generation/caching feature silently produces nothing or produces suspiciously-identical output across different inputs, check the code path before assuming the input data is unsuitable.

**WikiEval comparison — litmus's judge vs. Ragas's own metrics, on the RAGAS paper's own benchmark (Es et al., EACL 2024, `ragas.pdf` in repo root).** The paper reports RAGAS accuracy on WikiEval (50 Wikipedia-derived Q/context/answer examples with pre-built contrastive good/bad pairs) as: faithfulness 0.95, answer relevance 0.78, context relevance 0.70 (their Table 4, judged by `gpt-3.5-turbo-16k`). Script: `eval_study/wikieval_comparison.py`; dataset now lives at `vibrantlabsai/WikiEval` on HuggingFace (renamed from `explodinggradients/WikiEval`); results in `results/wikieval_comparison/`. All judged by the same fixed `azure/gpt-5.4` deployment used throughout this study (stronger than the paper's original judge model, so absolute numbers aren't directly comparable to 2024 — but litmus-vs-Ragas *within this run* is a fair comparison, same judge for both).

| Dimension | litmus | Ragas (this run) | Ragas (paper, 2024) |
|---|---|---|---|
| Faithfulness | **0.98** (48 win/2 tie/0 loss) | 0.98 (49/0/1) | 0.95 |
| Answer relevance | **0.87** (C1 proxy: 37/13/0) | 0.53 (22/9/19) | 0.78 |
| Context relevance | n/a (no litmus metric) | 0.50 (0/50/0 — pure ties) | 0.70 |

- **Faithfulness: litmus is genuinely competitive with Ragas's own faithfulness metric on Ragas's own validation set** — both ~0.98, both above the paper's originally reported 0.95. litmus's F1-F3 (mean yes-rate) and Ragas's `Faithfulness` (statement-decomposition + NLI, same core method the paper describes) produce essentially equivalent discrimination here.
- **Answer relevance: litmus's closest proxy (C1, "does the answer address the question that was asked") clearly outperforms Ragas's current `AnswerRelevancy` implementation** (0.87 vs. 0.53, also below the paper's own 0.78). **Root cause confirmed** (`ragas/metrics/collections/answer_relevancy/`): the metric asks the LLM to generate a question the *answer* addresses, then compares that generated question to the original via embedding cosine similarity, plus a `noncommittal` flag for evasive/vague answers ("I don't know", "it depends"). WikiEval's `poor_answer` examples exploit exactly the gap this leaves: e.g. for "When is the PSLV-C56 launch and where from?", the poor answer is *"The scheduled launch date and time... have not been provided. The PSLV-C56 mission is an important space mission... aims to launch a satellite to study weather patterns."* — this restates the question's topic almost verbatim (high embedding similarity) and makes concrete claims rather than hedging (so `noncommittal=0`), while still failing to answer. The metric structurally cannot distinguish "on-topic but non-answering" from "on-topic and answering" — it measures topical alignment, not answer adequacy. litmus's C1 (direct LLM judgment: "does this answer address the question") catches this immediately because it isn't going through an embedding-similarity proxy. Independent of embedding model choice (verified logically from the code path, not just observed) — swapping `all-MiniLM-L6-v2` for `text-embedding-ada-002` would not fix this, since the failure is in what's being compared, not how.
- **Context relevance: Ragas's own `ContextRelevance` metric scored exactly 0.50 — a dead tie on every single one of the 50 examples** (`context_v1` vs. `context_v2`, the latter padded with irrelevant back-link sentences; directly verified on example 1: both score 1.0/1.0 despite `context_v2` being 47% longer). **Root cause confirmed** (`ragas/metrics/collections/context_relevance/util.py`): both judge prompts score on a 0/1/2 scale where the instruction is *"If the context contains **any** relevant information to answer the question, say 2"* — the max score triggers on presence of relevant content, with no penalty for surrounding irrelevant padding. Since `context_v2` is `context_v1` plus padding, the relevant content is still fully present, so both score the ceiling rating. This metric measures **recall** (is the answer in here somewhere), not **focus/precision** (is the context free of noise) — despite the name, and despite the original 2024 paper's version explicitly targeting focus ("extract the sentences that are crucial, divide by total sentences" — a metric that *would* penalize padding, and which was removed from the current `ragas` codebase entirely in favor of this redesigned dual-judge version). litmus has no comparable metric to check this against.
- **Bottom line:** litmus is not merely "structurally different" from Ragas (guaranteed coverage vs. proven quality) — on faithfulness specifically, it performs *equivalently* to Ragas on Ragas's own published validation benchmark, and on answer relevance it currently outperforms Ragas's shipped implementation. This is a genuinely positive, directly-comparable result, distinct from Study 1's RAGTruth calibration (κ=0.48, a much harder/more realistic benchmark) and Study 2's generation-quality comparison (mixed, corpus-dependent) above.

**Study 2, 2x scale-up (corpus A: 50→100 docs / 135→266 chunks; corpus B: 20→40 MuSiQue instances / 372→723 chunks).** Re-ran litmus + Ragas generation and scoring at roughly double the original Study 2 size, to check whether the corpus-A result (Ragas beating litmus on scoring-health spread) holds up with more data. `*_v4.json` suffix in `results/corpus_a_enterpriserag/` and `results/corpus_b_musique/`; separate `.litmus_cache_a_v2`/`.litmus_cache_b_v2` cache dirs used out of caution (checkpoint-scoping fix from bug #3 above makes this unnecessary now, but cheap insurance).
- **Corpus A (100 docs):** litmus generated 48 records (15 single_chunk, 14 cross_doc, 10 unanswerable, 9 adversarial; 50 bridge-entity candidates, up from 23) — `scoring_health()` = "broken" (faithfulness 0.04, correctness 0.23, abstention 0.25). Ragas generated 47 rows — `scoring_health()` = "needs_work" (faithfulness 0.17, correctness 0.17, abstention 0.23). **Ragas's advantage narrowed at 2x scale**: correctness went from litmus-trails-by-0.10 (0.13 vs 0.23) to essentially tied (0.23 vs 0.17), though Ragas still leads faithfulness spread (0.17 vs 0.04).
- **Corpus B (40 MuSiQue instances, 723 chunks):** litmus generated 29 records (203 bridge-entity candidates found, up from 96 at the smaller size — MuSiQue's curated cross-entity structure showing through strongly with more data) — `scoring_health()` = "broken" (faithfulness 0.0, correctness 0.21, abstention 0.10). Ragas generated 22 rows (its slowest run this session: KG-generation over 723 nodes took roughly 90+ minutes, vs. ~40 min for corpus A's 266 nodes) — `scoring_health()` = "broken" too (faithfulness 0.0, correctness 0.05, abstention 0.05). **litmus now clearly leads on correctness discrimination at this corpus/scale** (0.21 vs 0.05) — the reverse of corpus A's pattern. Both sets still saturate on faithfulness (0.0/0.0) — same root cause as before, `SimpleRAG` rarely fabricates regardless of question difficulty on this corpus.
- **Verified clean:** zero question overlap between corpus A's (48) and corpus B's (29) litmus results — the checkpoint-scoping fix (bug #3) held even without the extra `cache_dir` isolation.
- **Taking both corpora together:** the "Ragas beats litmus on scoring-health spread" result from the original (1x) Study 2 run does **not** generalize uniformly — it holds on corpus A (EnterpriseRAG-Bench/GitHub PRs) at both sizes, but corpus B (MuSiQue) flips to favor litmus at 2x scale on correctness while both are similarly faithfulness-saturated. This looks corpus-dependent rather than a consistent litmus-vs-Ragas ordering — plausibly related to MuSiQue's cross-doc-heavy structure interacting differently with litmus's now-substantial bridge-entity coverage (203 candidates) there than on GitHub PR text. Table 2/3 in `results/tables/` reflect the original 1x sizes; these 2x numbers are documented here rather than overwriting those tables, since both are legitimate, differently-scoped runs worth keeping.
